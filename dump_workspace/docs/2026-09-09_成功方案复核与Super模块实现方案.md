## 1. 可复用经验（已由实测验证）

### 1.1 先做事实勘验，再选路线

失败的根本原因是**假定目标构建仍暴露标准反射接口**。正确顺序是：

1. 枚举 `GameAssembly.dll` **实际导出**（不要照抄 SDK 头文件）；
2. 把导出分成 bootstrap 组与反射 getter 组，确定最小可用集合；
3. 检查 `global-metadata.dat` 魔数/熵，魔数不对就不走离线 Dumper 路线；
4. 反汇编参考 DLL，确认它是 API 遍历、结构游走还是混合。

实测导出结论（日志 `[0]` 段）：

| 类别 | 结果 |
| --- | --- |
| `get_corlib` / `image_get_class` / `image_get_class_count` / `image_get_name` / `image_get_assembly` | 可解析 |
| `class_for_each` / `class_get_fields` / `class_get_methods` / `domain_get` / `domain_get_assemblies` / `assembly_get_image` | 全为 0 |

### 1.2 最小 bootstrap + 结构游走

只把 4 个 bootstrap 函数当必需条件，字段/方法/属性/接口/父类/类型全部由结构偏移读取。
这样在「导出裁剪 + metadata 加密」的双重加固构建上仍然可用。

### 1.3 自动校准而不是硬编码偏移

**本次最大的工程价值**。实测校准结果证明：本构建布局与 Unity 2019.4 标准布局**不一致**，
硬编码必然出错。校准器按候选偏移打分并写日志：

```
[cal] fields off=0x80 stride=0x20 score=36/96
[cal] methods off=0x98 score=62/96
[cal] method_tail token=0x40 flags=0x44 iflags=0x46 slot=0x48 params=0x4A score=211/213
[cal] props off=0x90 stride=0x28 score=20/96
[cal] ifaces off=0xA8 score=0/96          <-- 失败，缺陷 2 的根因
[cal] field_count off=0x11C score=41/41
[cal] method_count off=0x118 score=71/71
[cal] property_count off=0x11A score=23/23
[cal] parent off=0x58 ok=96/96
[cal] calibrated=1
```

### 1.4 工程化要点（照抄即可）

- `DllMain` 只创建工作线程，配置/目录/文件/等待/容器全放工作线程（避开 loader lock）。
- `GetModuleHandleA` 1 ms 轮询、最长 60 s，覆盖注入时机问题。
- `MemReader` 区域缓存 + `SafeCopy`（SEH）统一安全读。
- SEH 边界隔离到**无 C++ 展开对象**的薄包装函数（解决 MSVC C2712）。
- Writer 大缓冲 + 周期性 flush；日志每行立即 flush（进程被踢也保留证据）。
- 日志标记固定：`[0] [1] [cal] [meta] [2] [3] [4] [CRASH]`，排查顺序 `[0]→[1]→[cal]→[2]→[3]→[4]`。

### 1.5 通用排查顺序（9 步，已验证有效）

1. 确认 Unity Mono / IL2CPP 与版本线索；
2. 枚举实际导出；
3. 分 bootstrap / 反射两组；
4. 查 metadata 魔数与熵；
5. 反汇编参考 DLL 判定机制；
6. 最小探针验证 `get_corlib → image_get_class_count → image_get_class → name`；
7. 多样本校准结构偏移，再扩到字段/方法/属性/接口；
8. 把注入时机、反作弊存活窗口、每类工作量当独立变量；
9. 最后才优化输出格式与数量对比。

## 2. 实测证据：本构建真实布局 ≠ 标准布局

日志的校准值 + dump 的症状互相印证，可推出本构建的结构位移。

### 2.1 Il2CppClass 尾部 +8 位移（高置信推断）

| 字段 | 标准（2019.4） | 本构建实测 | 差值 |
| --- | --- | --- | --- |
| `image` | 0x00 | 0x00 | 0 |
| `name` / `namespace` | 0x10 / 0x18 | 0x10 / 0x18 | 0 |
| `parent` | 0x58 | 0x58 | 0 |
| `fields` | 0x80 | 0x80 | 0 |
| `properties` | 0x90 | 0x90 | 0 |
| `methods` | 0x98 | 0x98 | 0 |
| `implementedInterfaces` | 0xA8 | 0xA8（数组仍在） | 0 |
| **`flags`** | 0x108 | **0x110（推断）** | **+8** |
| **`token`** | 0x10C | **0x114（推断）** | **+8** |
| `method_count` | 0x110 | **0x118** | +8 |
| `property_count` | 0x112 | **0x11A** | +8 |
| `field_count` | 0x114 | **0x11C** | +8 |
| `interfaces_count` | 0x11C | **0x124（推断）** | +8 |

> 依据：`method_count/property_count/field_count` 三项校准值全部 +8，且三项评分满分
> （71/71、23/23、41/41），说明「0xC8 之后整体后移 8 字节」。
> 症状印证：若按 0x108 读 flags，读到的值不是 TypeAttributes，
> 于是 **56214 个类里 47949 个被印成 `internal class`**、`[Serializable]` 出现 0 次。
> 验证方法：注入探针读 `klass+0x110`，对 `GameObject`/`Camera` 等已知 public 类
> 应得到 `0x00100001`（Public|Sealed 等），读 `+0x114` 应得到 `0x0200xxxx` 形态 token。

### 2.2 MethodInfo 同时保留 rgctx_data 与 methodMetadataHandle

| 字段 | 标准 | 本构建实测 |
| --- | --- | --- |
| `methodPointer` / `invoker_method` / `name` | 0x00 / 0x08 / 0x10 | 0x00 / 0x08 / 0x10 |
| `klass` / `return_type` / `parameters` | 0x18 / 0x20 / 0x28 | 0x18 / 0x20 / 0x28 |
| （新增第 8 个指针） | — | 0x30 与 0x38 各一个指针 |
| `token` | 0x38 | **0x40** |
| `flags` / `iflags` | 0x3C / 0x3E | **0x44 / 0x46** |
| `slot` / `parameters_count` | 0x40 / 0x42 | **0x48 / 0x4A** |

> 依据：`[cal] method_tail ... score=211/213`（213 个样本里 211 个通过），
> 且 dump 中方法修饰符（`public static`、`protected`、`virtual/override/sealed`）
> 与 `Slot` 数值均正常，证明尾部校准正确。方法名正常说明 `name` 仍在 0x10，
> 所以多出的 8 字节位于 `parameters`(0x28) 与 `token`(0x40) 之间。

### 2.3 `parameters` 是 `ParameterInfo[]` 而非 `Il2CppType*[]`

- 日志 `runtimeParamNames=333556`、`synthParams=31583`：绝大多数参数名来自运行时
  参数记录，说明 `parameters` 指向的是带名字的 `ParameterInfo` 数组（步长 0x18，
  name@+0x00，type@+0x10）。
- 但引擎**逐参数猜测**「先试紧凑 `Il2CppType*[]`，失败再试 ParameterInfo」，
  当 `ParameterInfo` 的第 0 个字（name 指针）偶然通过 `looksLikeType` 时被误判为紧凑形式，
  于是出现类型错乱（见 3.4）。

## 3. 复核发现的 6 处系统性缺陷

| # | 缺陷 | 证据（实测 dump / log） | 根因 | 修复方向 |
| --- | --- | --- | --- | --- |
| 1 | 类修饰符几乎全错 | 47949 × `internal class`、5067 × `internal enum`、`[Serializable]` 0 次；`GameObject`/`Camera` 印成 `internal class` | `cFlags` 用 0x108，本构建实际在 0x110 | 增加 flags/token 校准（评分见 4.4） |
| 2 | 基类/接口列表串入垃圾 | `SecurityParser : SmallXmlParser, IContentHandler, Object, SmallXmlParser`、`X509Certificate : ISerializable, Object, X509Certificate, ...`、出现 `6$` | `ifaces off=0xA8 score=0/96` → 接口数组未通过校验，`iface_count` 落到 0x11C（其实是 field_count），按字段个数从 0xA8 多读 | 先修 flags 校准（`looksLikeInterface` 依赖 flags），再把 iface_count 候选扩到 0x130，并用 `typeHierarchy` 交叉验证 |
| 3 | 类类型名大面积退化 | `' Class '` 出现在 219707 行、`Type0` 8893 行；`Find(String)` 返回 `Class`、`get_scene_Injected(out Type0 ret)` | `Il2CppType.data` 对 T_CLASS/T_VALUETYPE 常为**类型定义索引**而非 klass 指针，`klassName(小整数)` 失败 → 回退 `Class`；索引越界/位串为 0 时 → `Type0` | 自适应 data 语义：小值按索引解析（见 4.3），并发现 `s_TypeInfoTable` |
| 4 | 参数类型错乱 | `ManagedStreamRead(Byte[] buffer, Int32 offset, Byte[] p2, Class stream, IntPtr returnValueAddress)`（真值应为 `int count, Stream stream`） | 逐参数猜测紧凑/ParameterInfo 布局，紧凑分支误命中 | 全局一次性判定参数布局（按方法级命中率打分），不再逐参猜 |
| 5 | metadata 未定位 | `[meta] not found -> synthetic param names`、`synthParams=31583` | 魔数反向扫描 64 MiB 上限内未命中（内存副本头部可能被改写） | 改用 `klass->typeMetadataHandle` 的 `nameIndex` 字符串比对定位；失败则依赖 `ParameterInfo` 名 |
| 6 | 安全读开销大 | `vq=17430429`（1743 万次 VirtualQuery） | `rdStr` 逐块 probe、扫描逐 qword probe | 大块 probe + 批量读取；区域缓存合并；扫描时按 64 KiB 批读 |

> 说明：缺陷 1–4 都属于「校准未覆盖」而非路线错误。方案本身（最小 bootstrap + 结构游走）
> 已被实测证明可行，这 6 项是把产物从"可用"提升到"接近参考效果"的收尾工作。

## 4. Super 模块实现方案（`GameAssembly_Super.dll`）

### 4.1 Super 变体与普通体的差异

| 项 | 普通体 | Super 体 |
| --- | --- | --- |
| 模块名 | `GameAssembly.dll` | `GameAssembly_Super.dll` / `GameAssembly_Super_IBT.dll` |
| 保护 | 无 | VMProtect（`.vmp0/.vmp1`） |
| il2cpp 导出 | 4 个 bootstrap 可用 | **全部不可用**（`GetProcAddress` 全 0） |
| 参考 DLL | 可用 | 同样受限（硬编码 `GameAssembly`） |
| 运行时结构 | 明文可读 | **仍然明文可读**（il2cpp 运行时在跑） |

**结论**：Super 模块不能依赖任何 il2cpp 导出，必须把"引导"换成**纯内存结构发现**，
而结构游走与校准部分可以 100% 复用现有引擎。

### 4.2 总体架构

```
① 模块发现（无导出）      PEB/Ldr 枚举 + PE 头校验 + 名称匹配
        ↓
② 类型表发现（关键）      扫描 s_TypeInfoTable：连续 Il2CppClass* 数组
        ↓
③ 镜像发现               由 klass->image 去重 + Il2CppImage 结构校验
        ↓
④ 布局校准（复用+扩展）    fields/methods/props/ifaces/counts/flags/token/method_tail
        ↓
⑤ 类型名解析（修复缺陷3） data 指针/索引双语义 + 索引→klass 表回查
        ↓
⑥ 参数解析（修复缺陷4）   一次性判定 ParameterInfo[] vs Il2CppType*[]
        ↓
⑦ 输出（完全复用）        dump.cs / log.txt，格式与参考一致
```

### 4.3 关键步骤细节

**① 模块发现（无导出）**

```text
优先：GetModuleHandleA("GameAssembly_Super.dll") / GetModuleHandleA("GameAssembly.dll")
回退：PEB 遍历 Ldr->InLoadOrderModuleList，按 BaseDllName 子串匹配 "GameAssembly"
再回退：扫描已提交可读区域中的 PE 头（MZ + e_lfanew 合理 + SizeOfImage 合理）
       且 FileHeader.Machine==0x8664，配合"模块内存在 .dll 名称字符串表"打分
产出：moduleBase / moduleSize（RVA 计算基准）
```

**② 类型表发现（`s_TypeInfoTable`，Super 的"无导出引导"）**

IL2CPP 2019+ 用 `s_TypeInfoTable`（`Il2CppClass**`，按全局 TypeDefinitionIndex 索引）
缓存所有类。它在堆上是一段**长连续指针数组**，长度 ≈ 全部类数（本构建 56214），
这是唯一可靠且不依赖导出的类枚举入口。

发现与校验（伪代码）：

```cpp
bool IsKlass(uintptr_t k) {
  if (!mem.probe(k, 0x140)) return false;
  char nm[256]; if (!klassName(k, nm)) return false;         // name@+0x10 合法标识符
  if (!NameLooksValid(nm)) return false;
  uintptr_t img = mem.rdPtr(k + cImage);
  if (!LooksLikeImage(img)) return false;                     // image@+0x00 合法
  // 决定性自校验：klass->byval_arg.data == klass 且 type ∈ {CLASS, VALUETYPE}
  uint32_t bbits = mem.rdU32(k + 0x20 + tBits);
  uint32_t bte = (bbits >> 16) & 0xFF;
  if (bte != T_CLASS && bte != T_VALUETYPE) return false;
  if (mem.rdPtr(k + 0x20 + tData) != k) return false;
  // this_arg 同样自引用（再加固一次）
  uintptr_t pa = mem.rdPtr(k + cParent);
  if (pa && !mem.probe(pa, 0x40)) return false;
  return true;
}

// 扫描：找最长的「连续 qword 均为 IsKlass 或 0」的区间
for (region : readableRegions)
  for (p = region.lo; p + 8 <= region.hi; p += 8)
    if (IsKlass(*(uintptr_t*)p)) {
      // 向前后扩展，统计连续有效项数
      if (runLength >= 64) 记录为类型表候选 (base=p, len=runLength)
    }
// 交叉验证：候选表长度 ≈ Σ image.typeCount；且 table[image.typeStart] 的 klass->image == image
```

> 若该表被拆成多段或未连续，退化为「全内存 klass 结构扫描」：对所有可读区域做
> `IsKlass` 过滤并按 `klass->image` 分组，仍能枚举全部类（只是失去索引顺序）。

**③ 镜像发现**

`klass->image` 已经给出镜像指针集合；再用现有 `looksLikeImage`（name 以 .dll/.exe 结尾、
`typeStart/typeCount` 合理、`assembly->image` 反向指针一致）校验、按 `typeStart` 排序，
即可在无 `image_get_name` 的情况下得到镜像名（直接读 `image+0x00` 的字符串）。

**④ 校准扩展（同时修复普通体的缺陷 1、2）**

在现有校准器上新增三类评分：

```text
flags/token：候选 0x100..0x130
  评分 = Σ samples[
      (flags & 7) <= 7                                  // 可见性位合法
      && (flags & 0x00000020 || flags & 0x00000080 || flags & 0x00000100)   // 至少一个常见位
      && (token & 0xFF000000) == 0x02000000             // TypeDef token 形态
  ]
interface 数组/计数：候选 0xA0..0xB8 / 0x110..0x130
  评分 = Σ samples[ 连续 N 项均满足 flags & TA_INTERFACE 且 name 合法 ]
  交叉验证：条目名不应与父类名/本类名重复（当前垃圾串的主要特征）
参数布局：一次性全局判定
  for mode in {ParameterInfo(0x18,name@0,type@0x10), ParameterInfo(0x18,name@0,type@0x08), compact(Il2CppType**)}
      score = Σ methods[ 所有参数 type 合法 && 参数名合法率 ]
  取最高分模式，写入 log（不再逐参猜测）
```

**⑤ 类型名解析（修复缺陷 3）**

```cpp
// 先判定本构建 Il2CppType.data 语义
//   ptrMode:  data 指向 Il2CppClass
//   idxMode:  data 是 TypeDefinitionIndex（< 类型总数）
// 判定依据：统计 T_CLASS 类型的 data 中「可 probe 且 IsKlass」的比例
//           与「小整数且 < typeCount」的比例
uintptr_t ResolveKlass(uintptr_t data) {
  if (ptrMode && IsKlass(data)) return data;
  if (idxMode && data < typeTableLen) return typeTable[data];   // s_TypeInfoTable 回查
  if (IsKlass(data)) return data;                               // 兜底
  return 0;                                                     // 输出 "Class" 之外的占位
}
```

这样 `T_CLASS`/`T_VALUETYPE` 的名称解析不再依赖游戏是否"顺手"解析过该类型，
可消除当前 219707 行 `Class` 与 8893 行 `Type0`。

**⑥ 输出**：完全复用现有 Writer / 格式，不改动已验证的排版。

### 4.4 无导出端到端自测（可在无游戏环境下验证）

已有 `App/Il2CppRuntimeDumper/synth/` 骨架，改造为 Super 验证台：

| 组件 | 作用 |
| --- | --- |
| `GameAssemblyStub.cpp` → `GameAssembly_Super.dll` | 构造合成结构，**不导出任何 il2cpp_*** |
| `SyntheticUnityHost.exe` | 加载桩并驻留，暴露 PID |
| `Injector.exe` | 真实 `CreateRemoteThread + LoadLibraryA` 注入 |
| `MemoryStructDumper.dll`（Super 模式） | 走无导出引导，产出 dump.cs |
| 断言 | 类数/字段数/方法数/RVA/修饰符/接口/类型名与桩的期望值逐项比对 |

这条链路能覆盖：模块发现、类型表扫描、`IsKlass` 校验、校准、参数布局判定、输出格式。
桩里再故意加入「flags 位移 +8」「MethodInfo 双指针」「data 为索引」三种变形，
即可在离线环境复现并验证全部 6 项修复。

### 4.5 风险与降级

| 风险 | 表现 | 降级策略 |
| --- | --- | --- |
| `s_TypeInfoTable` 不连续/未找到 | 类型表扫描 0 命中 | 退化为全内存 klass 结构扫描（`IsKlass` 过滤 + 按 image 分组） |
| VMProtect 改动结构 | 校准分数全 0 | 输出 `[cal]` 全量候选评分表，人工/自动挑最高分；不扩大盲目扫描 |
| 模块被隐藏 | 模块发现失败 | PE 头扫描 + 名称字符串打分；RVA 基准退化为"最小方法指针页对齐" |
| NEAC 存活窗口 | 中途被踢 | 单线程一次性完成；大缓冲；先输出类名+字段，再补方法与属性（分阶段 flush） |
| metadata 仍不可得 | 参数名缺失 | 依赖 `ParameterInfo` 名；不足则合成 `p0..pN` 并计数入日志 |

### 4.6 交付物与验收标准

交付：

