# dump_all 产物分析与扩展可行性

日期：2026-09-10。任务范围：分析 `F:\gua\dump\dump_all` 的生成方式及当前 SuperDumper 的扩展可行性，暂不实现。

本次只新增这份分析记录；没有修改 C++、Python、配置或 DLL，也没有运行参考 DLL、注入目标进程或重新构建。

## 1. 结论

可以在现有 SuperDumper 的基础上扩展出类似的多文件产物。目录中的功能分为类型结构与地址索引、运行时字段及配置数据、进程与模块快照三部分；它们需要的数据来源不同。

现有结构游走和类型解析可以支撑第一部分及后续数据读取的定位。配置表实际内容、静态字段当前值、完整虚函数表和枚举常量还需要增加专门的读取、校准与校验，不能仅靠把 dump.cs 换一种格式输出。

参考目录的文件种类较全，但已经发现明显的数据错误、命名冲突和未命中结果，不宜把它的全部数值作为正确基准。

## 3. 生成工具与实现证据

### 3.1 可以确认的内容

`normal/full_dump8.log` 第一行标记 `variant=Plain`；`super/full_dump8.log` 第一行标记 `variant=Super-VMP`。日志按 Stage 0、Module 1 至 Module 16 分阶段运行，最后记录完成。

目录还包含工具自身的内存镜像：

- `super/modules/full_dump_74D9.dll.dump`
- `normal/modules/full_dump_770B.dll.dump`
- `normal/modules/full_dump_7800.dll.dump`

静态检查 Super 工具镜像发现：

- 它是 x64 原生 PE DLL，CLR 数据目录为 0，内存镜像长 4,714,496 字节。
- 可见导入来自 USER32.dll 与 KERNEL32.dll，包括模块/线程快照、VirtualQuery、GetProcAddress、文件操作等。
- `.rdata` 内存在与日志一致的 `full_dump8`、Config Table Dump、BinaryDesignData Config Dump 等格式字符串。
- 日志显示类型反射 getter 多项为零，仍使用 get_corlib、image_get_class、image_get_class_count 等少量入口引导，再校准 FieldInfo / MethodInfo 和镜像步长进行结构游走。
- 普通样本校准到镜像步长 0x50、方法名 +0x10；Super 样本校准到镜像步长 0x48、方法名 +0x18。这与“普通和 Super 需要不同布局处理”的现有结论一致。

这些证据支持它是一套原生运行时游走加多种导出模块的工具。

### 3.2 不能由现有证据断言的内容

检查范围内没有发现 full_dump8 的源码、工程、可用 PDB 路径或明确仓库标识，不能确定它对应哪个开源项目，也不能排除使用了静态链接的库。

工具镜像中虽然能搜索到 Mono.Cecil 字符串，但所检查的 `Mono.Cecil.Mixin.ZeroVersion` 位于可写 `.data` 的运行时内容区域，而非实现模块的只读字符串区域；其中还混有已经格式化的 dump 文本。它不能证明 full_dump8 使用了 Mono.Cecil 作为依赖。

本次完成的是产物、日志、PE 头、导入表、字符串及当前源码的交叉分析，未完成工具机器码的全面还原。现有 dumpbin 对该内存镜像的反汇编因缺失代码地址范围表失败，因此不把尚未验证的内部控制流当作确定结论。

## 4. 配置表的两条导出路线

### 4.1 静态 Dictionary 扫描

日志明确记录：扫描所有类，寻找含静态 Dictionary 的类，然后导出字典数据。

- 普通样本报告找到 801 个候选类。
- Super 样本报告找到 687 个候选类。
- 这些是候选数，不等于成功生成的独立配置表文件数。

config 目录包含框架类型、各种缓存甚至 Dictionary 自身的结构字段，说明这一阶段的范围比“游戏配置表”更广。例如 Super 的 `ActorKit.tsv` 列名是 `_buckets`、`_entries`、`_count` 等，并非 ActorKit 的普通业务字段。

如果实现，应使用实际 Dictionary 对象及其封闭泛型信息确定键、值和 Entry 布局，检查有效条目、空槽及空值，并记录数据属于哪个类的哪个静态字段。不能对任何泛型 Dictionary 都套相同 Entry 大小。

### 4.2 BinaryDesignData 入口

Super 日志第 1336 行开始记录第二阶段：定位 `CBinaryDesignDataReader`，得到 `s_Inst`，逐表输出。

- 普通日志：1987 个表，550167 行。
- Super 日志：1973 个表，477367 行。

当前自研 dump 也已经包含以下真实结构：

```text
BinaryDesignData.CBinaryDesignDataReader
    private static CBinaryDesignDataReader s_Inst
    public SkillConfig_Skill_BinaryReader SkillConfig_Skill
    ...许多其他配置 Reader 字段...

BinaryDesignData.SkillConfig_Skill_BinaryReader
    m_Key2Indexer  +0x10
    m_Cache        +0x18
    m_Buffer       +0x20
    m_PtrPadding   +0x28
    GetDataCount()
    GetData(Int32)
    Exists(Int32)
    Foreach(...)

BinaryDesignData.SkillConfig_Skill
    _ID, _SkillIcon, _CdDuration, _ExcelFightPropertyList, ...
```

这证明本项目已经具备定位 Reader 和解释数据对象字段的基础。扩展时可从经验证的静态字段区取 s_Inst，按名字定位各 Reader，再读取其缓存或底层数据并按对象类型输出。

必须另行确认：参考工具是否只导出了已加载的 m_Cache，还是还解析 m_Buffer / 调用了 Reader 来补齐尚未实例化的记录。本次证据不足以确定这一点。只读取缓存时，行数会受到运行时加载状态影响；GetDataCount、键索引、缓存有效条目数和实际导出数需要分别记录，才能判断完整性。

当前样本与参考样本结构已有版本差异：当前 SkillConfig_Skill 多出 `_ComboConditionId`，CBinaryDesignDataReader 的表字段也存在增删。不能直接复制旧 Reader 字段偏移。

## 5. 参考结果中已确认的问题和疑点

### 5.1 枚举值严重异常

Super 的 `enums.tsv` 共 15608 条，其中 15028 条值为同一个 `-923166912`。普通版共 14337 条，其中 13928 条值为 `-540524944`。

具体例子：Super 的 FractureByMotionType，Dodge、Fall、CrossWindow 等成员在 enums.tsv 中均为同一个异常负值，而参考 dump.cs 把这些成员全部输出成 0；两份产物自身也不一致。

这高度符合常量读取路径或地址解释错误，但本轮没有还原该读取函数，不能断言具体哪一行指针计算出错。枚举常量不能当成普通 static_fields 内存偏移为零的字段来读取。当前自研版本尚未输出枚举数值，后续必须增加正确数据源，不能冒用这些参考值。

### 5.2 接口数据混入非接口内容

普通版 `interfaces.txt` 的 SecurityParser 项混有 System.Object、类自身、问号等；Super 的 FracturedComponent 项混有方法名和不可打印内容。

可能涉及接口数组、计数或指针解释错误。当前核心已经具有接口布局校准和名字/父类/重复项过滤，新增独立文件应复用这些结果。

### 5.3 class_meta 的方法数不可信

Super 的 56395 行类型信息中，有 15244 行 MethodCount 恰好为 500；该列总和为 11511768，与同一日志报告的 542994 个导出方法明显不一致。

例如最前面的匿名类在 TSV 中计为 500 个方法，但对应 dump.cs 只有少量方法。这说明元数据摘要使用的计数读取/限制规则没有与正文一致校准。

普通版该列总和也达到 1976545，而日志方法数为 514962。不能直接拿这个文件验证当前 Dumper 的方法完整度。

### 5.4 vtables.txt 有两种序号

每个目标类先输出普通方法列表，之后才出现 `--- raw vtable (...) ---` 和 `vt[...]`。

因此普通方法清单中的 `[0]`、`[1]` 不是虚函数槽位。Super raw 区块还多次出现固定 257 slots，正确性需要校准后确认，不能只凭名字叫 vtables.txt 就接受全部位置和数量。

当前 naraka_offset_report.hpp 只对指定历史位置检查可执行指针和相邻 MethodInfo 配对，并保留 CANDIDATE；它还没有实现完整表起点、槽数、每槽函数/MethodInfo/继承关系的导出。

### 5.5 配置文件命名冲突

普通版摘要有 2377 行，但只有 2332 个 TSV；其中 45 条摘要都指向 `__c.tsv`，另有 Assert.tsv 重复。

Super 摘要有 2307 行，但只有 2302 个 TSV。System.Numerics.Hashing.HashHelpers 和 System.Collections.HashHelpers 等记录共用 `HashHelpers.tsv`。

多个不同记录对应同一个文件，无法保持一一对应，存在覆盖或数据混淆问题。新实现应把程序集、命名空间、完整嵌套类型、字段身份纳入输出标识，另保留清晰的摘要索引。

### 5.6 嵌套数组可能被错误解释

SkillConfig_Skill.tsv 的 `_ExcelFightPropertyList` 出现 `[1718145632,402]` 等内容，参考结构把该字段降级为 object[]，而当前结构准确识别为 ExcelFightProp[]。

这两个整数可拼成 `0x1926668D260`，具有该次运行中用户态指针的形态；普通样本也有类似现象。这强烈提示对象引用可能被拆成两个 Int32 输出，但仅凭 TSV 尚不能完全还原其读取路径，应标为待验证的解析问题。

新序列化器必须区分原始数值数组、引用数组、值类型数组和嵌套数组，不宜统一按四字节元素读取。

### 5.7 字符串“常量全集”并未成功

日志明确说 literal API 不可用，转为扫描静态字符串字段。普通样本 `string_literals.txt` 第二行还出现 `Boolean.FalseLiteral -> True` 的确定错误。

因此这份文件只能作为部分静态字符串快照参考，不能称作完整字符串常量导出结果。

### 5.8 部分文件只表示扫描已运行

Super 的 erp_offsets.txt 是零字节；两份 xrefs_sendtosync.txt 都写着 `Scanning 0 targets`。这不证明相关业务地址不存在，只说明该轮规则没有获得有效结果。

日志完成标记也不能替代逐模块的结果验证。

## 6. 模块镜像的解释边界

GameAssembly 镜像文件大小等于该次运行的 SizeOfImage。节区表中许多节的 RawAddr / RawSize 为零，内存布局与磁盘 PE 布局不一致。

所以这些文件首先是模块内存快照，不能因为扩展名为 DLL 就认定是可直接加载的 DLL、已重建的原始程序或已完整恢复的 metadata。

Super 日志报告成功读取 434470912 字节，磁盘文件长 434475008 字节，相差 4096 字节；日志还写着 `4096 zero-filled unreadable pages`。结合总大小，至少其“pages”标签与计量单位存在歧义，不能直接解释成 4096 个页面。新实现应分别记录不可读字节数、页面数和具体 RVA 区间。

`neac/NeacSafe.sys` 在日志中的动作是 Kernel Driver Copy / COPY，表明这里是磁盘驱动文件副本，不能等同于已经获取内核实时内存。

普通参考同样包含 .vmp 节，因此变体判断不能只看是否存在 .vmp。当前 SuperDumper 已优先按 GameAssembly 模块身份判断，这一路线应保留。

## 7. 建议的后续实现顺序

1. 先扩展结构索引：class_meta、rva_map、all_bases、interfaces。复用现有遍历和校准结果；保留地址类型、所属模块及可靠性状态。
2. 再扩展运行时静态值及少量代表性配置表：以 CBinaryDesignDataReader 为主要入口，先验证字符串、标量、容器和嵌套对象，再推广到更多表。区分没有加载、空表、不可读和解析失败。
3. 单独解决枚举常量和完整虚函数表：分别校验常量来源、底层整数宽度，以及虚表起点、真实槽数和 MethodInfo 配对。
4. 最后添加可选模块镜像及进程诊断文件。这部分 I/O 最大，应与常规结构导出独立控制。

建议一次运行对应一个带时间戳的目录，保留 dump.cs 已有时间戳与偏移摘要协议，并增加产物清单、模块标识、各阶段计数与简体中文日志。这只是设计建议，本轮没有实施或改变现有输出约定。

验证时应按相同游戏版本和相同加载阶段比较：类型字段数、实际表数、有效行数、未加载记录、失败记录，以及代表性字段的类型和值。当前自研 v7 为 123 个 Image、56495 类，参考 Super 为 118 个 Image、56395 类，不能直接用两个不同样本的文件大小或方法总数判定优劣。
