# 注入式 IL2CPP 结构 Dump 成功经验总结

> 日期：2026-09-09  
> 项目：`F:\gua\UnityExplorer-main`  
> 参考产物：`F:\gua\dump\Unity-Offset.dll`、`F:\gua\dump\dump2026.09.03.cs`  
> 最终状态：自研 DLL 已由用户实际注入验证可用。

## 1. 目标与最终结论

本次工作的目标不是做一个只能够枚举少量对象的探针，而是构建一个效果尽量接近
`Unity-Offset.dll` 的注入式 IL2CPP dumper，输出包含以下内容的 `dump.cs`：

- 程序集/镜像和 TypeDefIndex；
- 类名、命名空间、继承关系、接口、类标志；
- 字段名、字段类型、访问属性和实例偏移；
- 属性及其 get/set 状态；
- 方法名、返回类型、参数类型、参数名、RVA/VA、Slot 和方法标志。

最终采用的方案已经达到预期：

```text
少量仍可用的 IL2CPP 导出
        -> 运行时镜像发现
        -> image_get_class / image_get_class_count 枚举类
        -> 直接读取进程内已解密的 Il2CppClass 等结构
        -> 自动校准字段/方法/属性数组布局
        -> 生成 dump.cs 和 log.txt
```

最终 DLL：

- `F:\gua\UnityExplorer-main\bin\Release\Il2CppRuntimeDumper.dll`
- `F:\gua\UnityExplorer-main\bin\Release\MemoryStructDumper.dll`

两者当前构建产物内容一致，均为 Release|x64，大小约 240 KiB。用户已完成实际注入测试并确认没有发现问题。

## 2. 之前为什么达不到参考效果

### 2.1 旧实现依赖了目标构建不存在的导出

最初的实现沿用了标准的反射 getter 路线，要求解析下列函数：

```text
il2cpp_domain_get
il2cpp_domain_get_assemblies
il2cpp_assembly_get_image
il2cpp_class_get_fields
il2cpp_class_get_methods
il2cpp_class_get_name
il2cpp_field_get_name
il2cpp_method_get_name
```

但对目标进程中的 `GameAssembly.dll` 做 `GetProcAddress` 分类探针后，结果明确分成两组：

| 类别 | 结果 |
| --- | --- |
| `il2cpp_get_corlib`、`il2cpp_image_get_class`、`il2cpp_image_get_class_count`、`il2cpp_image_get_name`、`il2cpp_image_get_assembly` | 可解析 |
| `class_for_each`、`class_get_name`、`class_get_fields`、`class_get_methods`、`field_get_name`、`method_get_name`、`domain_get`、`domain_get_assemblies` 以及 `mono_*` | 全部为 NULL |

这说明注入通道不是根因。旧 dumper 的校验器把 `class_get_fields` 和
`class_get_methods` 设为必需条件，而这两个导出在目标构建中根本不存在，所以程序必然在
解析阶段失败。

### 2.2 磁盘 metadata 也不能作为离线退路

检查两份 `global-metadata.dat`：

| 文件 | 头四字节 | 标准值 |
| --- | --- | --- |
| 普通体 metadata | `0x57CA7923` | `0xFAB11BAF` |
| Super 体 metadata | `0x57ED9D83` | `0xFAB11BAF` |

文件头不是标准 IL2CPP metadata 魔数，内容也呈现高熵特征。因此，直接把文件交给普通
Il2CppDumper/Il2CppInspector 的离线解析路线不能工作。目标构建同时做了导出裁剪和 metadata
加密，不能假设磁盘文件仍然保留明文结构。

### 2.3 注入时机确实是问题，但不是最终根因

逆向参考 DLL 时发现它会反复执行：

```cpp
while (!GetModuleHandleA("GameAssembly.dll"))
    Sleep(1);
```

因此最初曾判断自研 DLL 只是注入太早。增加等待和重试后，核心导出可以稳定出现，但类型
反射导出仍然全部为空。这个过程很重要：

- “等待 `GameAssembly.dll` 出现”是必须的健壮性措施；
- 但等待不能补回被目标构建裁剪掉的导出；
- 必须通过探针把时机问题和能力缺失问题区分开。

### 2.4 逐类做重型检查会触发进程保护

早期探针在每个类上重复调用 `VirtualQuery`、重复读取大量字段并立即写文件，
`CreateRemoteThread + LoadLibraryA` 通道下容易超过 NEAC 的存活窗口，表现为进程被踢出或
首次枚举尚未完成就退出。快速批量枚举类名可以完成，增加每类工作量后则不稳定。

这属于性能和注入通道限制，不是结构解析根因。最终方案通过区域缓存、大缓冲增量写入、
减少每类重复检查，并保留 CE 注入作为验证主通道解决了这个问题。

## 3. 如何找到真正原因

### 3.1 逆向参考 DLL 的导入、字符串和反汇编

对 `Unity-Offset.dll` 做了导入表、字符串和关键函数反汇编检查，得到三条证据：

1. 它是原生 x64 C++ 注入 DLL，使用 `GetModuleHandleA`、`GetProcAddress` 和 `Sleep`，不是简单的 Mono.Cecil C# 直读器。
2. 模块发现采用 1 ms 轮询，直到 `GameAssembly.dll` 在进程中出现。
3. dump 驱动函数除了调用少量导出外，还大量使用 `GameAssembly` 基址加固定偏移直接读取运行时结构。

同时在 DLL 中发现了 `H:\C++Code\il2CppRuntimeDumperEx\...\il2cpp_dump.cpp` 等源码路径。

### 3.2 确认参考 DLL 的开源来源

本地克隆并对照了开源项目
[shalzuth/Il2CppRuntimeDumper](https://github.com/shalzuth/Il2CppRuntimeDumper)，位置为：

```text
F:\gua\UnityExplorer-main\dump_workspace\Il2CppRuntimeDumper_src\
```

该项目提供了注入、程序集/类遍历、字段/方法/属性建模和输出重建的基础思路，
也是 `Unity-Offset.dll` 的重要来源线索。

需要区分两个层次：开源源码展示的是通用的 `domain_get`、`class_get_fields` 等 API 路线，
而本次参考 DLL 的实际二进制针对加固目标做了适配，最终关键成员读取不能依赖那些被裁剪的
getter，而要直接读取进程内运行时结构。因此不能只复制开源 API 清单，必须以目标进程的
实际导出表和内存布局为准。

### 3.3 使用 DiagProbe 做导出分类探针

探针把导出分为三组：

- bootstrap：`get_corlib`、`image_get_class`、`image_get_class_count`、`image_get_name`；
- 参考 DLL 可能使用的类型反射函数；
- 旧实现要求的 domain/assembly/field/method 函数。

结果证明 bootstrap 组正常，反射组全部为 NULL，所以结论从“注入过早”修正为：

> 目标 IL2CPP 是“导出裁剪 + metadata 加密”的双重加固构建。

### 3.4 使用 StructWalkProbe 确认运行时结构

在不调用缺失 getter 的前提下，只使用四个 bootstrap 导出：

1. `il2cpp_get_corlib()` 获取 corlib 镜像；
2. `il2cpp_image_get_class_count()` 获取类数量；
3. `il2cpp_image_get_class()` 获取每个 `Il2CppClass*`；
4. 直接读取类结构中的指针并用合法类名、父类和类型指针反向校验。

探针先确认了 corlib 的 1825 个类可以完整枚举，再逐步确认 `Il2CppClass`、`FieldInfo`、
`MethodInfo` 和 `PropertyInfo` 的数组位置与元素步长。这个过程避免了盲猜结构后直接输出错误
数据，也避免了继续调用不存在的 API。

### 3.5 从单类样本扩展到完整镜像

确认结构基础后，扫描 corlib 所在分配块、已发现镜像所在分配块以及 `GameAssembly` 的可读
内存区域，按以下条件识别镜像：

- 镜像名可读且类似 `.dll`/`.exe`；
- `typeStart` 和 `typeCount` 在合理范围；
- 镜像对应的 assembly 反向指针一致；
- `image_get_class_count` 返回合理的类数量；
- 镜像名称去重后按 `typeStart` 排序。

这一策略最终发现 `Assembly-CSharp.dll`，并成功枚举其 39102 个类。这个结果证明“运行时
结构游走”不是只对 corlib 样本有效，而是可以覆盖游戏主程序集。

## 4. 最终解决方案

### 4.1 只用可用导出作引导

当前版本仅把以下函数作为必需 bootstrap：

```text
il2cpp_get_corlib
il2cpp_image_get_class
il2cpp_image_get_class_count
il2cpp_image_get_name
```

`il2cpp_image_get_assembly` 作为可选信息使用。字段、方法、属性、接口、父类、类型和参数
等其余内容全部由内存结构偏移读取，不再要求被裁剪的反射 getter 存在。

### 4.2 运行时结构布局

以下是本次 Unity 2019.4 系目标构建上已验证并用于默认 profile 的布局。它们不是所有 Unity
版本的通用常量，版本变化时必须重新校准。

| 结构 | 字段 | 偏移/步长 |
| --- | --- | --- |
| `Il2CppClass` | `image` | `+0x00` |
| `Il2CppClass` | `name` | `+0x10` |
| `Il2CppClass` | `namespace` | `+0x18` |
| `Il2CppClass` | `parent` | `+0x58` |
| `Il2CppClass` | `typeMetadataHandle` | `+0x68` |
| `Il2CppClass` | `fields` | `+0x80` |
| `Il2CppClass` | `properties` | `+0x90` |
| `Il2CppClass` | `methods` | `+0x98` |
| `Il2CppClass` | `flags/token` | `+0x108 / +0x10C` |
| `Il2CppClass` | `method/prop/field/iface count` | `+0x110 / +0x112 / +0x114 / +0x11C` |
| `FieldInfo` | `name/type/parent/offset/token` | `+0x00 / +0x08 / +0x10 / +0x18 / +0x1C` |
| `FieldInfo` | 元素步长 | `0x20` |
| `MethodInfo` | `ptr/name/klass/return/parameters` | `+0x00 / +0x10 / +0x18 / +0x20 / +0x28` |
| `MethodInfo` | `token/flags/implFlags/slot/paramCount` | `+0x38 / +0x3C / +0x3E / +0x40 / +0x42` |
| `PropertyInfo` | `parent/name/get/set/attrs` | `+0x00 / +0x08 / +0x10 / +0x18 / +0x20` |
| `PropertyInfo` | 元素步长 | `0x28` |
| `Il2CppType` | `data/bits` | `+0x00 / +0x08` |

### 4.3 自动校准而不是固定相信默认值

`il2cpp_dump_core.hpp` 会从最多 96 个有效类样本中评分候选布局：

- 字段数组：检查字段名、类型指针、父类指针、偏移范围和元素步长；
- 方法数组：检查方法名、所属类、返回类型和方法指针；
- 属性数组：检查属性名、所属类及 get/set 方法；
- 接口数组：检查接口标志和合法类名；
- 计数字段：用实际识别出的数组长度反推 `u16` count 偏移；
- 方法尾部：在多个候选 profile 中校准 token、flags、slot 和参数数量；
- 父类偏移：通过父类名合法性重新验证。

校准结果和评分会写入 `log.txt`。当目标 Unity 版本改变时，先看校准日志，而不是直接修改
输出格式或盲目增加扫描范围。

### 4.4 参数名和类型的降级策略

参数名不是所有运行时结构都直接保存，因此实现按以下顺序选择：

1. 能定位到运行时 metadata 时，优先使用 metadata 参数名；
2. 使用 `ParameterInfo` 中的运行时参数名；
3. 两者都没有时生成 `p0`、`p1` 等合成名称。

参数结构同时兼容 `Il2CppType*[]` 紧凑形式和 `ParameterInfo[]` 形式；`ref`/`out` 由类型位和
参数属性判断。这样即使 metadata 仍被加密，也不会因为参数名缺失而丢弃整个方法。

### 4.5 输出格式

输出为与参考 `dump.cs` 便于对照的纯文本格式：

- 普通实例字段：`// offset:0x...`；
- `const` 字段：`// size:0x...`；
- 方法：`// RVA: 0x... VA: 0x...`，有槽位时附加 `Slot: ...`；
- 属性输出 `get;`、`set;` 或两者；
- 类头保留 `Image`、`Namespace`、`Instance` 和 `TypeDefIndex` 信息。

相较于 Mono.Cecil 重建 Dummy DLL，这种格式更适合直接与
`F:\gua\dump\dump2026.09.03.cs` 做行级和数量级对照。

## 5. 工程实现中的关键修复

### 5.1 不在 DllMain 中做复杂工作

`DllMain` 只做线程通知关闭和创建工作线程。配置读取、目录创建、文件打开、模块等待、
容器初始化和结构遍历全部放在工作线程中，避免在 loader lock 内使用 C++ 容器和文件系统。

### 5.2 模块等待策略

工作线程每 1 ms 检查一次 `GetModuleHandleA("GameAssembly.dll")`，最长等待 60 秒，记录等待
时间。这样既覆盖参考 DLL 的注入时机，也避免永久阻塞。

### 5.3 安全读和区域缓存

`MemReader` 通过 `VirtualQuery` 建立可读区域缓存，统一提供指针、整数和字符串读取；
`SafeCopy` 用 SEH 保护单次内存复制。区域缓存减少重复 `VirtualQuery`，对大规模类遍历尤其重要。

### 5.4 异常边界

MSVC 不允许在含有需要 C++ 展开的对象的函数中直接混用复杂 SEH，因此把真正的 `__try / __except`
放在无 C++ 局部对象的薄包装函数 `RunDumpWithSeh` 中。遇到坏指针时记录 `[CRASH]` 并中止 dump
线程，不主动终止游戏。

### 5.5 输出缓冲和配置

写出器使用大缓冲和周期性 flush，避免每个字段都触发文件 I/O。DLL 同目录配置支持：

```text
outdir=...
images=...
fields=0/1
properties=0/1
methods=0/1
instance=0/1
metadata=0/1
outheuristic=0/1
maxclasses=N
```

没有配置时回退到 DLL 同目录的 `out`，避免依赖开发机固定路径。

## 6. 日志系统设计与阅读顺序

用户要求后续能够根据运行日志协助分析，因此 DLL 会在输出目录写入 `log.txt`，同时发送
`OutputDebugStringA`。日志文件打开后每行立即 flush，进程异常退出时也尽量保留前面的证据。

重点标记如下：

| 标记 | 含义 |
| --- | --- |
| `[0]` | PID/TID、输出目录、GameAssembly 基址/大小/路径、bootstrap 导出地址和缺失导出探针 |
| `[cal]` | 样本数量、字段/方法/属性/接口候选偏移、步长、计数偏移和评分 |
| `[meta]` | metadata 是否定位成功以及参数表偏移；失败时转运行时/合成参数名 |
| `[1] images` | 发现的镜像数量、名称、`typeStart` 和类数 |
| `[2] dumping` | 当前镜像、类数和起始 TypeDefIndex |
| `[3] DONE` | 类、字段、方法、属性、接口、跳过类、输出字节数和安全读统计 |
| `[4] result` | 最终 `OK` 或 `FAIL` |
| `[CRASH]` | 结构读取触发的 SEH 异常码，表示 dump 线程已被隔离 |

推荐的日志排查顺序是：`[0]` -> `[1]` -> `[cal]` -> `[2]` -> `[3]` -> `[4]`。如果 `[0]` 的
bootstrap 已成功而 `[cal]` 分数为 0，优先考虑 Unity 版本或结构重排；如果 `[0]` 就缺少 bootstrap，
再检查模块名、注入时机和目标变体。

## 8. 可复用的排查顺序

以后遇到“参考 DLL 能 dump、自研 DLL 不能”的情况，建议严格按以下顺序排查：

1. 先确认目标是 Unity Mono 还是 IL2CPP，并记录 Unity/metadata 版本线索。
2. 枚举 `GameAssembly.dll` 的实际导出，不要只看 SDK 头文件或网络文章中的函数列表。
3. 将导出分为 bootstrap 和反射 getter 两组，先确认最小可用集合。
4. 检查 metadata 魔数和熵；魔数不对时不要继续走普通离线 Dumper 路线。
5. 反汇编参考 DLL，确认它到底是 API 遍历、运行时结构游走，还是两者混合。
6. 用最小探针验证 `get_corlib -> image_get_class_count -> image_get_class -> name` 链路。
7. 通过多个真实类样本校准结构偏移，再扩展到字段、方法、属性和接口。
8. 把注入时机、反作弊存活窗口和每类工作量作为独立变量测试。
9. 最后才优化输出格式和数量对比，避免在错误数据源上反复修饰文本。

## 9. 版本变化时的注意事项

- `Il2CppClass` 布局、`MethodInfo` 尾部和参数结构会随 Unity/IL2CPP 版本变化；默认偏移只对当前
  已验证构建负责。
- 目标可能改名为 `GameAssembly_Super.dll` 或使用其他保护层；此时模块等待和 bootstrap 名称
  需要重新确认。
- 反作弊可能改变可读区域或注入线程存活时间；优先使用已验证的 CE 注入通道，并尽量让一次
  dump 在单个线程窗口内完成。
- `metadata` 不应作为字段/方法枚举的唯一来源。它在本方案中只是参数名增强来源，找不到时应
  继续输出结构信息。
- 发现镜像数量、校准分数、类数量明显异常时，应保存完整 `log.txt`，不要先扩大指针扫描范围；
  扫描范围过大本身可能增加运行时风险。

## 11. 经验总结

本次失败的关键不是“少写了几个 API 调用”，而是错误地假定目标构建仍然暴露标准 IL2CPP
反射接口，并把加密 metadata 当成可直接解析的明文文件。真正有效的做法是先对参考产物和目标
进程做事实勘验：确认可用导出、确认 metadata 状态、确认运行时结构，再选择最小 bootstrap 加
结构游走。最终版本因此不再依赖被裁剪的 getter，也不把 metadata 作为唯一前提，同时用校准、
缓存、日志和异常隔离把一次性的逆向发现固化成了可维护的 DLL 工程。
